# Vendor-neutral improvement loop

The comparison is the work product. A prettier report is not evidence that authorized adoption improved the receiver. **Reusable lesson: avoid comparison-to-report-only drift** by cycling `compare → authorized useful increment → observable proof → updated comparison`.

Any vendor can refine the skill. Sharing refinements upstream is a community practice, not a licence restriction; the MIT grant governs copying and modification. Maintain the shared canonical package according to the host's discovery/versioning procedure. Preserve explicit user scope and genuine authority throughout.

1. Record the actual user variant, package revision, permitted actions, trial artifact and observed flaw. Keep private material private; use a synthetic reproduction for shareable explanation. Do not invent a failure to justify a preferred rewrite.
2. Reproduce the flaw through a realistic public behavior seam: requested comparison → actual output/decision or receiver task. For documentation guidance, use a usage trial rather than a wording-mirror test. For a necessary helper, follow the host's TDD contract: one independent-oracle public failing slice → minimal passing implementation → next slice; mock only real external boundaries. Never retrofit RED provenance.
3. Correct the smallest causal ambiguity, missing step or example. Avoid adding universal rules for every anecdote, new scanners/frameworks, or duplicated report/disclosure policy. Feedback itself authorizes neither product changes nor external sharing.
4. Retain old evidence. Increment the package version and record revision/date, observed flaw, changed guidance, before/after evidence and remaining limits. Keep detailed evidence history here; any release changelog should summarize the release and point here rather than duplicate its full narrative.
5. Rerun the affected variant plus adjacent trigger/nontrigger cases and at least one valid exception (for example, receiver already satisfies the outcome or a pure computation needs no durable effect record). Record actual outputs. Two clean consecutive rounds or an explicitly documented accepted residual risk qualify the tested scope, not every vendor/environment.
6. Use an independent blind receiver recheck when the change affects interpretation/adoption. Give only the safe package, realistic request and minimum synthetic artifacts; no intended answer or diagnosis. Preserve reconstruction/execution and failed/unknown checks. Parent or independent reviewers may separately qualify native discovery/runtime integration.
7. Return the refinement and its evidence to the comparison/handoff. Separate authored, validated, committed/pushed, landed, installed, enabled, executed and independently understood states. No automatic global installation, production mutation, publication or send follows from feedback.
