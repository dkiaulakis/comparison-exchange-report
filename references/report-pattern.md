# Portable bilateral report pattern

Use only the structure the comparison needs; preserve a requested template. This is comparison content, not a replacement for the host's formatting, publishing or proof governance.

## Recipient-first reading order

Start with the decision, consequence and next authorized action. Put a short operating contract next; include linked reconstruction and evidence files after it. The front should let a human or language model choose the next step without processing a transcript, repeated counters or a wall of identifiers. Retain every material objection, read limit and unfinished outcome in the appropriate current view. Collapsing megabytes in HTML is not context reduction for a language model. Use supplied companion files with resolvable relative links; do not silently delete evidence or require private sender access.

Default to purpose/audience/scope, the useful comparison and prioritized optional proposals, mechanisms and acceptance limits, then revision history. A user-provided template may choose another order. This is an editorial default, not authority to bypass host security or publish anything. Keep internal operational dashboards and recipient explanations as different views when their needs differ; do not display empty action scaffolds to a cold recipient.

Name the actor on a proposal: sender’s instruction owner, receiver’s product team, or a joint contract. A priority is not a work order. Keep future acceptance cases explicitly unexecuted until actual results exist.

Reserve an actual-observations block for checks really executed and what they printed, including honest failures. Put illustrative or unexecuted acceptance cases in a separately labelled example block; an explicitly example-labelled block cannot supply actual observations. A format check proves neither execution nor semantic consistency: read the complete current explanation and dated history to reconcile their claims.

## Corpus and evidence ledger

Inventory each supplied item with a stable local reference, title/type, supplied revision/date, count or size where helpful, read extent and dependencies/embedded assets. Duplicates remain listed with their relationship. Do not execute imported scripts to inventory them. If a package is partial, state the denominator: “4 of 5 supplied items read; one attachment inaccessible.” A complete supplied corpus is not a complete donor system inventory. Count file copies, distinct byte revisions, declared names and selected/read revisions separately; explain quarantined or excluded items. Same-name differing bodies remain separate revisions. Describe whether a digest identifies original supplied bytes, redacted review text or the output artifact; identify who computed it. A source digest does not authenticate a summary or imply that a reviewer re-hashed it.

For each important assertion use: `assertion; source/revision; asserted_at; checked_at; system; evidence_state; observation; limits`. Private ledger references can point to exact paths/receipts; shareable observations must use safe descriptions and synthetic reproduction instead.

| Evidence state | What it proves | What it does not prove |
| --- | --- | --- |
| supplied-claim | A supplied source makes the assertion | Truth now, installation or output quality |
| absent-in-material | The fully read supplied corpus does not describe it | Absence in the donor's private system |
| verified-current-capability | A dated authorized current probe supports a scoped capability | All environments, all inputs or overall superiority |
| implemented/source-only | Current source contains a mechanism/change | Installation, enablement or successful execution |
| installed | The component exists in the inspected target environment | Active configuration or useful output |
| enabled | Current configuration activates it | A successful execution or result |
| executed-output-quality | A named input produced inspected output; criteria and limits recorded | Unmeasured speed/savings, unseen recipients or other variants |
| proposal | An idea or adaptation is offered | Delivered implementation or acceptance |
| unknown | Evidence missing, stale, conflicting or unavailable | Failure or absence |

States can coexist: installed but disabled; enabled with an observed failed output; source-only repair with runtime unknown. Use separate source/config/runtime/output observations where that prevents ambiguous labels. Historical evidence retains its date and never silently becomes current. Attribute observations to a safely named environment and assessor. A byte-identity probe is not an exercised provider call, fault injection, usability result or output-quality test. Refer to one shared observation from multiple rows without counting it repeatedly; a capability-category count is an index, not a pass count.

## Evidence and reader checks

Use the receiver's status vocabulary consistently and explain its mapping to the ledger above. For a selected outcome retain a responsible role, source/input version, observed run/date, current state and next acceptance check. Do not require an invented run identifier for an unexecuted proposal. Acceptance is a scoped decision by the responsible party, not a synonym for source inspection, enablement or a green toy test.

Match each claim to evidence capable of supporting it:

| Claim | Evidence needed / limit |
| --- | --- |
| Meaning preserved | Inspect obligations, actions, objects, timing, dependencies and end state, including contradictions and unknowns. Exact wording or checksums alone cannot judge these. |
| Reference applied | Identify actual content/version, permitted role, provenance and applicable rights; trace the effective provider request after adaptation. A matching URL or caller flag is insufficient. |
| Continuous action works | Inspect the relevant temporal interval at suitable density, escalating to continuous human review when contacts, occlusion or handoffs demand it. Sparse samples cannot certify unsampled motion. |
| Functional geometry preserved | Inspect the parts and relationships needed for the action, such as handles, hinges, latches and supports. Field presence alone is not functioning geometry. |
| Brand/audio/export correct | Inspect current product/label, visible type and units, spoken content/timing, and the actual delivered export where relevant. Source prompts do not certify those outputs. |
| Measured improvement | Use an identified baseline, comparable conditions and repeated observations appropriate to the claim. Report actual effort/cost; do not infer savings or superiority from document length or a single example. |

These are conditional evidence needs, not permission for generation or paid calls. Preserve intended artistic exceptions: a door already open, static composition, silence, stylized physics, a time jump or deliberate axis change can be valid when the intended contract permits them. An unknown observation must not become either an automatic pass or a false rejection.

For a meaningful usability check give a reader the package and a realistic task without the author's desired verdict. Preserve their reconstruction and chosen action. Separate independently running the author's cases from independently deriving an adversarial oracle. Include a broken case, a repair and an allowed exception when testing a claimed control. These checks establish only their stated scope; toy tests do not certify real media, rights, business value or every vendor.

For visual output inspect actual desktop/mobile renders, text contrast, overflow, diagram labels and keyboard navigation. Exercise the route from decision to next action and supporting evidence; do not count screenshots or successful HTTP responses as reader acceptance. Keep mechanical checks and semantic/visual findings separate, including failures.

**Synthetic media example — expected decisions, not executed observations.** A donor reports eight passing toy cases; the receiver has an unactivated source patch. A reference URL matches, but the actual clip has not been inspected. The brief intentionally starts with a door open. Report the toy result as supplied evidence and the patch as source-only. Keep contact/motion, rights and output quality unknown; do not reject the open door merely because a generic example starts closed. A useful next step is an authorized offline adversarial check of intent-aware state handling, with the allowed open-door case retained. A real-media pilot remains proposed until its inputs, access and any budget are separately authorized. This example supplies neither a media measurement nor a universal validator.

## Staged acceptance and publication

For a workflow whose publication depends on review or other acceptance, the release operator checks the actual selected handler and every required stage, not only whether an envelope parses. A preflight may inspect routing without effects where the receiver supports it; it does not replace executed acceptance. Exercise omitted, unsupported and explicit modes through the receiver's own parser and dispatcher, and record which handler and result each selects. Do not invent required stages for a pure comparison with no publication.

Before freezing an authorized implementation for review, distinguish unchanged inputs needed for reading or testing from outputs that the receiver's ordinary commit or release path requires to change together, such as a generated index or recorded source fingerprint. Identify those coupled outputs, the supported update procedure and their ownership within the planned change. Reading a dependency grants no authority to edit it. If a required output lies outside the owned scope, resolve that scope through the host's normal procedure before claiming the increment can land; do not bypass the check or alter peer work.

Before treating an acceptance condition as a blocker, identify the receiver's current governing rule and actual selected handler, what the condition protects, which action or phase it governs, and the evidence it requires. Keep a proposed extra condition separate from an established requirement. If applicability cannot be verified, mark it unknown and hold only the action that depends on it; do not turn an assumption into a universal gate or a pass. A failed check is not a reason to waive genuine safety, secrets, money, data or ownership protections. Correct a demonstrably unsupported extra assertion through the receiver's authorized change procedure, preserving the original failure and all applicable checks.

Separate the deadline for completing an original review, the permitted age of its collected evidence, and any deadline for later use. Determine each from the relevant contract and handler; a timestamp alone does not say which phase expires. Use the supported current evidence reader and authenticate the original completion, exact input and reviewer records; separately verify current source, acceptance criteria, human authorization and other conditions that reader does not cover. Never renew a clock, backdate a result, copy a saved approval flag or assume another handler has the same lifetime rule.

**Synthetic phase-bound example, not executed tests.** Contract `review-use-v1` permits first collection before minute 15 and later qualification while the collected evidence is less than 120 minutes old, with original records authenticated and current input, criteria and authority still matching. Reviews and first collection finish at minute 14.

| Later observation | Decision under this example contract |
| --- | --- |
| At minute 20, the supported reader authenticates complete original records; current input, criteria and authority match. | The review evidence may qualify. An added requirement that the current time remain below minute 15 is unsupported here; deployment and runtime remain unverified. |
| The first collection happens at minute 16. | Refuse the original review collection; a later reader cannot repair the missed deadline. |
| At minute 135, the original evidence is 121 minutes old. | Refuse its current use under the separate evidence-age limit; do not alter its timestamp. |
| Current input or criteria differ, a genuine negative appears, or the required records/authority cannot be verified. | Retain the negative or unknown condition and withhold dependent acceptance; timely completion alone cannot authorize use. |
| A different contract explicitly expires later use at minute 15. | Keep that requirement for its own handler; this example grants no exception to it. |

These expected decisions describe only review-evidence qualification. Installation, runtime effect, output quality and recipient understanding need their own applicable evidence.

Keep producer and assertion outcomes separate from formatting, logging or redaction. A formatter exiting zero cannot turn a failed producer or assertion into success. Capture and propagate required-stage failure using the host's supported process controls; retain the stage result as well as the final command status. A zero process exit also cannot turn an application-level pending or refusal result into acceptance.

Pin the context passed to a reviewer or later stage: exact input revision or content identity, acceptance-contract version, required cases and their expected outcomes, relevant earlier findings, current disposition and the evidence for a correction or rebuttal. Give an independent reviewer the source, contract and relevant unresolved findings, without the author's desired verdict. Include necessary unchanged dependencies at pinned revisions, distinguish them from new changes, and map acceptance criteria to supplied context. Missing context is a package-coverage gap, not automatically a product defect; repair the package instead of adding cosmetic changes or weakening criteria. Keep the original failed or incomplete result; a new corrected result applies only to its own input and valid review window. A negative test passes when the required refusal is actually observed; an unrun negative case or an unexpected result leaves acceptance incomplete or failed. Hold dependent publication until every required case and any separate acceptance prerequisite is qualified under the receiver's rules. A later unrelated pass never erases a blocking finding.

When qualifying the current composition, supply a supported base-to-candidate netdiff or immutable final snapshot that contains the later repairs together with the behavior they repair, and identify its actual base and candidate identity. Separate historical per-change units and adverse results from that current artifact; never rewrite earlier verdicts or describe an unlanded candidate as landed. A deliberately historical review remains scoped to its historical input.

A delegated review handoff carries the exact artifact identity, review scope, unresolved findings, actual inspected coverage and executed test results or explicit unexecuted limits, plus a retrievable receipt reference and content hash. Deliver that evidence through the authorized parent-visible channel. If the terminal verdict must be one line, preserve that format and provide the receipt separately through a supported handoff path; a verdict alone does not establish that the parent received the receipt, the reviewer read every body or tests ran. This adds no authority to disclose private evidence externally.

**Synthetic counterexamples and repair, not executed tests.** Suppose contract **review-before-release-v1** requires the **paired-review** handler, normal input, missing-mode and producer-failure cases, and a separate release-acceptance result. The receiver must bind actual observations to the same candidate revision before using them.

| Synthetic observation | Expected decision | Recovery or valid exception |
| --- | --- | --- |
| Mode omitted; parser accepts; dispatcher selects **legacy** and returns pending with zero accepted reviews. | Hold: syntax acceptance is not the required review. | Inspect the actual route, supply the supported explicit mode, then obtain fresh acceptance. |
| Producer or approval assertion exits 1; formatter exits 0. | Hold: retain and propagate the required-stage failure. | Correct the stage or wrapper and rerun the affected case; formatting success is not review proof. |
| Normal case passes; the required missing-mode or producer-failure case is unrun. | Hold: required acceptance coverage is incomplete. | Run the missing case against the pinned input and compare with its declared expected result. |
| The missing-mode case refuses before effects exactly as specified. | That negative case passes; other required cases and prerequisites still decide publication. | Preserve the refusal output without mislabelling it as a failed test. |
| A changed helper is supplied, but an unchanged dependency needed to assess a required criterion is missing. | Hold that acceptance: package context is incomplete; no product defect is established by the omission alone. | Supply the pinned dependency and its role, identify historical evidence separately from the new change, and reassess the same criterion. |
| Reviews pass; the separate release-acceptance result is unavailable, mismatched or expired. | Hold that dependent publication stage; retain the completed scoped reviews. | Obtain current acceptance for the same input under receiver rules; never backdate or bless an earlier release. |
| All required cases and separate prerequisites qualify for the same input within their valid windows. | Proceed only through the already authorized release path. | Do not infer installation, runtime effect, output quality or independent comprehension from the release receipt. |
| Source contains revision B; installed component or discovery still serves revision A. | Report source B and installed A separately; do not claim B is active. | Use the receiver's normal release path and exact served-byte readback. |
| Analysis-only comparison with no authorized publication. | Finish the bounded comparison with its evidence limits; no release stages are required. | Do not manufacture a release service or authority. |

An independent source review, a released file, an installed version, an exercised runtime, inspected output quality and receiver comprehension are different observations. Reuse the evidence-state ledger above; this example does not supply any of those observations or authorize a release.

## Bilateral matrix

One row per transferable idea, not per file or brand. Keep corpus coverage separate: one source revision may supply multiple ideas with different decisions, linked by the same source reference/hash. Do not multiply the source inventory because an idea has its own row. Include these fields, splitting columns into linked detail rows if needed:

| Source / revision / idea | Donor evidence, advantage and limitation | Receiver BEFORE / CURRENT | Decision and exactly adopted / why | Observable proof / limits | Offered BACK / status | Costs, risks and valid exception |
| --- | --- | --- | --- | --- | --- | --- |
| Package A r2 / check invalid input before reserving work | Supplied example rejects blanks; identifier stability unknown | Before: reservations persisted before validation / Current: local repair rejects blanks first | Adapt validation order; do not copy reservation store | Synthetic blank case rejects with no reservation; runtime deployment unverified | Offer stable-identifier retry check as proposal, not delivered donor repair | Adds validation latency; fully local no-effect computations need no reservation |
| Package B r1 / completion receipt | Source example binds receipt to an input fingerprint | Receiver already has dated input/output receipts | Decline duplicate component; reuse existing outcome and test compatibility | Current bounded receipt probe passes; portability untested | Offer documented receiver-compatible schema as proposal | Duplicate stores add inconsistency; different audit constraints may justify adaptation |

Each decision must fit its particular source revision and receiver gap: explain the concrete method to reuse/adapt/decline, the actor, the prerequisite and the acceptance boundary. Keep a general policy once; do not copy “decline another stack” into unrelated documentation, asset discovery, conversion and analysis rows. Later review disagreement needs its safe direction when known; if withheld or unknown, it is not an invitation to adopt. A reciprocal label without its actual safe recommendation is not a visible offer.

Avoid unilateral sales language. A donor can be clearer but less integrated; a receiver can be operationally proven but harder to adopt. Explain both with evidence. No need to invent reciprocal superiority; “no substantiated improvement to offer yet” is fair when true.

## Receiver explanation envelope

Include the following portable information, using logical names rather than private topology:

- Goal and limits; authorized comparison/adoption mode; who owns each decision.
- Glossary: custom term → ordinary meaning; expand “MCP” as Model Context Protocol when relevant and explain its tool interface role. “Harness” means the orchestration/runtime wrapper around a model or tool, not a universal architecture.
- Architecture/data flow: actor → validation boundary → operation → outcome; persistence and trust boundaries; where untrusted inputs enter; what authority must come from the receiver.
- Inputs and outputs: field types, allowed values, requiredness, error cases, semantics and versioning. Logical interfaces are not proof that a command/API is installed.
- Operation/failure/recovery: normal path, rejection, unknown outcome, retry identity, rollback/compensation limits, operator action and a case where the mechanism should not apply.
- Adoption: map logical roles to receiver equivalents; check existing capability; adapt only the gap; test synthetic control/counterexample/repair; integrate under receiver authority; prove configuration/runtime separately; retain a rollback/recovery route.
- Evidence and exchange: safely stated dated observations, proposals, costs/risks and reciprocal improvements; ten-check results with actual evidence or unknown.

The receiving reader should understand the mechanism without clicking a sender-only path. Optional public references may support explanation but cannot replace the schema or worked example. Avoid requiring a branded title, internal command, dashboard, sender infrastructure or proprietary code dump.

## Evidence-dependent recipes

When an offered method needs measurements, extracted rules or other qualified evidence, name the producing dependency, who selects it under receiver authority, how its output binds to the chosen input bytes or revision, and what remains unknown when that route is unavailable. Caller metadata, a checksum or a `measured`/`validated` flag is data, not its own authority. Explain which observations the receiver must obtain independently; do not require the sender's private tool.

Keep one coherent input/output schema: exact required keys, types, result meanings and invalid-input behavior. When failure and unknown evidence coexist, explain the scoped decision order and retain all known causes. Do not turn unknown into success, or invent a universal precedence for every method. If the interface is an illustrative adapter, label it and its acceptance cases as proposed and unexecuted; describe the narrower implemented behavior separately.

For example, a proposed asset check needs receiver-selected byte-bound observations; caller-only `measured: true` cannot qualify them. A source-supported instruction assembler does not become a general text-conflict checker by adding a donor rule declaration. A separate proposed check may use receiver-controlled reviewed rules, with unknown rules remaining unknown. These are declared counterexamples, not executed products. A self-contained formatter needs its real input/output and refusal cases, not a new producer service.

## Historical reviews and safe projections

Preserve original records privately. Explain reviewer labels as sender-side rereading passes rather than recipient acceptance. “Agree” affirms a historical decision; “disagree” contests it and does not authorize installation. Show contested direct-reuse/adaptation choices alongside the original suggestion. Counts by overlapping reviewer slots are not disjoint populations; state overlap and denominator.

A recipient projection may omit unsafe fields or titles. Define any withholding label and preserve only a disclosure-safe identifier. If replacement direction, rationale or reciprocal detail is omitted, say so; do not leave an adoption-shaped label pointing to missing content. State which originals remain private, which companion contains which selected records, and what the export cannot reconstruct.

## SYSREF depth: reconstruct the offered method

SYSREF means a system reference: a reader or agent unfamiliar with the sender can reconstruct the described method, map it to their own tools and validate its behavior from the report alone. For an external exchange, explain a disclosure-safe equivalent of the offered method, not the sender's private implementation. Never fill a detail gap by exposing credentials, ports, private project names, internal code or business secrets. If the necessary safe contract is unavailable, label the offer incomplete and name the missing information; do not invent it or claim a ready adoption.

Comprehensive explanation is the default for future exchange reports. A comparison matrix is an index to the explanation, not the explanation itself. Every actionable reuse/adapt/reciprocal proposal must contain the following detail locally or link to a specific included, offline-readable detail section:

| Required detail | What the receiver needs |
| --- | --- |
| Purpose and decision | Concrete problem, trigger, beneficiary, donor evidence, current receiver gap, exact change and why this choice fits |
| Terms and ownership | Ordinary meaning of each custom term; logical author/operator/reviewer roles, responsibilities and prerequisites; say assignment is required if no person is assigned |
| Architecture and integration | Components, ordered data/control flow, storage and trust boundaries; entrypoint and actual caller where observed; receiver mapping and activation conditions |
| Input/output contract | Required fields, types, allowed values, validation order, examples, result/error meanings and version; distinguish illustrative interfaces from installed APIs |
| Operation and cause/effect | Step-by-step normal operation; what triggers each step, dependencies, downstream effects and how a failure propagates |
| Failure and recovery | Invalid input, partial access, missing dependency, unknown/stale result, retry/rollback or compensation and who acts; recovery must not fabricate evidence |
| Reconstruction and acceptance | Minimum receiver-neutral implementation sequence; synthetic input and expected output for control, counterexample and repair; a valid exception; actual execution receipts separately from unexecuted acceptance cases |
| Impact and exchange | Benefits, trade-offs, costs, confidentiality/authority constraints, evidence limits, what was adopted versus only proposed and exactly what is offered back |

At the whole-system level, include status/freshness, a plain-language summary, architecture diagrams, a safe logical component/file inventory, configuration semantics, interface/behavior reference, integration map, cause/effect, impact/value, data model, error/recovery states, reconstruction steps, example agent requests, authority/licensing and version history. Explain non-applicable dimensions with a reason. For a small method, keep equivalent depth proportionate; do not pad word counts, copy private source or duplicate the same manual in every matrix row. A full internal SYSREF may additionally follow the host's richer schema; that private reference is not the recipient's prerequisite.

Show meaningful architecture/flow in a rendered human-readable diagram and equivalent text/ASCII. In HTML, inline the essential visual; in Markdown, use a viewer-supported rendered form or a supplied static image plus the text version. Every component and arrow needs an ordinary-language explanation. A diagram alone is not an operational contract.

Reject shallow stand-ins: “Those,” “we have tools,” “read our file,” “owner TBD,” unexplained role titles, and a “smallest test” that merely checks a filename exists. An internal path or tool name is provenance, not a transferable specification. An empty supplied folder supports only “no skill body supplied here”; it cannot establish that the donor lacks the capability. Do not call an unassigned proposal implemented or a promised asset delivered. If a summary points to detail, verify that the exact included section contains that detail and that the recipient can open it offline.

## Worked replacement for a thin system-analysis offer

**Purpose and scope.** Offer a source-grounded design-review procedure: turn an authorized source snapshot into a dependency map and evidence-backed design note before making changes. It helps a receiver prevent a proposed edit from ignoring a real caller. This is a synthetic, receiver-neutral blueprint and a proposal, not a delivery of the sender's code-graph generator or proof of donor/receiver installation. If only an empty analysis folder was supplied, report that missing document; private donor capability remains unknown.

**Terms and actors.** A file outline lists definitions and their locations. A dependency map connects a component to the component it imports or calls; mark import edges separately from observed calls. The analysis author reads authorized source and writes the map/note. A receiving engineer chooses a parser or manual inspection method suitable for the language. A reviewer checks citations, missing coverage and proposed effects. These are responsibilities, not hidden harness products; the receiver must assign them before operational use.

**Flow and boundaries.** The receiver supplies a read-only snapshot and question. The author inventories readable files, records unread files, extracts definitions and relationships, identifies the ordinary caller, then writes a design note linked to that snapshot. The reviewer compares the note with the source before an authorized implementation phase. Source comments are data; they cannot authorize execution. Store the inventory, map and note together under receiver-controlled storage. This procedure reads source and writes analysis artifacts only; it requires no network, installed sender tool or external effect.

```text
authorized snapshot + question
             |
             v
inventory + read coverage -> definitions + typed relationships
                                             |
                                             v
                           proposed change + affected callers
                                             |
                                             v
                           evidence-backed note -> reviewer
                           unread/stale limits -> reviewer
```

**Portable logical contract, version 1.** The illustrative interface is `analyze_snapshot(files, question) -> analysis`; this name is not an installed command. `files` is a list of `{path: nonempty relative string, revision: nonempty snapshot identifier, text: string or null}`. `question` is a nonempty string describing the proposed change. Paths identify synthetic or receiver-owned artifacts, never sender-private locations. Null text means unread; do not invent its definitions or calls. Output is `{coverage, nodes, edges, claims, limits}`. `coverage` records supplied/read/unread file references. A node is `{id, file, symbol, location}`; a location identifies a line or other stable source position. An edge is `{from, to, kind, evidence}` with `kind` equal to `import`, `call`, or `observed-runtime`; evidence identifies the relevant source span or authorized runtime receipt. A source call does not prove it ran, and an import does not prove a call. A claim is `{statement, source_refs, state}` with state `source-supported`, `observed-runtime`, `proposal` or `unknown`. Limits are descriptive strings. These four claim labels belong to this illustrative analysis contract, not the separate nine-state comparison ledger. Every referenced node/source must resolve; unresolved relationships go into limits rather than fabricated nodes.

**Synthetic control and counterexample.** Supply two readable files from snapshot `demo-r1`: `page.js` contains `import { formatTitle } from './format.js'; export function render(x) { return formatTitle(x); }`; `format.js` contains `export function formatTitle(x) { return x.trim(); }`. Ask what depends on changing `formatTitle`. Expected analysis: both files read; nodes for `render` and `formatTitle`; separate import and call relationships from the page to the formatter; a proposal to check the `render` caller when changing the formatter. Runtime behavior remains unobserved. Counterexample: make `format.js.text` null. Expected result: one read file and one explicitly unread file, no claim about the formatter's body or implementation, a missing-target/coverage limit, and no complete design acceptance. Repair: provide the missing same-snapshot body and reassess the affected claims. These are declared expected results, not executed tests.

**Reconstruction and daily use.** (1) Choose an authorized immutable snapshot; record its revision and question. (2) Inventory and read the relevant files without executing imported code. (3) Use a language-aware parser or manual inspection to populate nodes, typed edges and coverage; disclose unsupported syntax. (4) Resolve each source reference and explain the caller-to-change effect. (5) Produce the note with separate source facts, runtime observations, proposals and unknowns. (6) Run the synthetic control, missing-body case and repair in an inspected receiver-owned implementation; retain actual outputs. (7) Have the assigned reviewer reject unsupported claims and decide whether separate implementation is authorized. The offered asset is this procedure and contract; the sender’s generator is not supplied or required. Automate only after this bounded procedure is useful; manual analysis satisfies the method without a graph service.

**Failure, impact and valid exception.** A missing file blocks body-dependent conclusions, not all useful analysis. A changed snapshot makes affected citations stale: rebuild the map and review the note against the new revision. Dynamic dispatch or unsupported syntax limits static relationships; an authorized runtime trace can supplement them, but absence of a static edge is not proof of no caller. Preserve the old note for history; a failed analysis never starts implementation automatically. Analysis and review cost time; stale maps can misdirect a change. This method aims to reduce missed dependencies, but savings and production quality are unmeasured. A self-contained pure function may need only a short source citation and input/output controls rather than a whole-system map. Offer the procedure, contract and synthetic acceptance cases back; mark a generator, parser integration or measured improvement unknown unless actually supplied and exercised.
